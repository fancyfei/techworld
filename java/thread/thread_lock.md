# Java 锁机制与实现

在计算机系统中，锁（lock）或互斥（mutex）是一种同步机制，用于在多线程环境中限制对资源的并发访问。锁的作用是保证同一时刻只有一个执行线程能够进入受保护的临界区，从而维持互斥与并发控制的正确性。

## 锁相关的概念

- 锁开销（lock overhead）：锁占用的内存空间，以及 CPU 初始化、销毁、获取和释放锁所花费的时间。
- 锁竞争（lock contention）：一个线程试图获取另一个线程已持有的锁时，就发生了锁竞争。
- 死锁（deadlock）：至少两个线程各自持有对方所需的锁，并相互等待对方释放，导致都无法继续执行。
- 锁粒度（granularity）：锁所保护的数据量大小。粒度大则开销小但竞争激烈，粒度小则开销大但竞争缓和。
- 竞态条件：多线程的核心矛盾是"竞态条件"，即多个线程同时读写某个数据。
- 竞态资源：竞态条件下多个线程争抢的数据即"竞态资源"。

解决并发问题常见的同步互斥机制有以下四种：

- 临界区（Critical Section）：同一时刻只允许一个线程执行的代码区域，进入临界区前要获得访问权限。
- 互斥体（Mutex，mutual exclusion）：同一时刻只允许一个线程持有的锁，持有者对资源具有独占访问权。
- 信号量（Semaphore）：通过一个计数器控制同时访问资源的线程数量，计数为 1 时退化为互斥锁，二元信号量（binary semaphore）即等价于互斥。
- 事件（Event）：用信号通知的方式协调线程，一个线程等待事件，另一个线程在条件满足时触发事件。

## 悲观锁与乐观锁

- **悲观锁**：获取数据时先加锁，确保数据不被其他线程修改。`synchronized` 关键字和 `Lock` 的实现类都是悲观锁，适合写操作多的场景。
- **乐观锁**：采用无锁编程，最常使用 CAS 算法，线程更新数据前先判断数据是否被其他线程修改过。Java 原子类（如 `AtomicInteger`）的递增操作就是通过 CAS 自旋实现的，适合读操作多的场景。

## 编译器对锁的优化

JIT 编译器（Just In Time Compiler）在动态编译同步代码时，可以使用**逃逸分析**技术判别程序中锁对象与线程的关系，并据此做两类优化：

- **锁消除**：如果一段同步代码只有一个线程使用锁对象，编译器就在编译时消除这段加锁逻辑，减少不必要的加锁消耗。
- **锁粗化**：如果发现前后相邻的同步块使用的是同一个锁对象，就把这几个同步块合并为一个较大的同步块，减少频繁申请与释放锁的开销。

## 线程的等待策略：自旋锁

对未获得锁的线程，可以选择不立刻阻塞，而是在原地等待，从而避免操作系统进程调度和线程切换带来的开销，这就是自旋锁：

- **自旋锁**：线程尝试获取锁时，如果锁已被其他线程占用，该线程不进入阻塞，而是执行空循环等待，间隔一段时间后再次尝试获取。
- **适应性自旋锁**：自旋的时间（次数）不再固定，而是由前一次在同一个锁上的自旋时间及锁的持有者的状态来决定。前一次自旋等待成功了，本次就进入自旋等待，否则直接进入阻塞状态。

计算机科学家们设计了多种排队自旋锁，如 Ticket Lock、MCS Lock、CLH Lock。

## 线程获取锁的策略：公平锁与非公平锁

为了减少唤醒线程的开销、提高整体吞吐，一种策略是让线程上来就直接尝试占有锁，尝试失败再去排队，这就是**非公平锁**。

**公平锁**的策略是：每个线程获取锁前先查看锁维护的等待队列，如果队列中有线程在等待，就加入队尾，按 FIFO 规则排队获取。

非公平锁中线程有几率不阻塞直接获得锁，CPU 不必唤醒所有等待线程，因此开销小、效率高，但可能让已经在等待中的线程等待过久。

Java 并发包中的 `ReentrantLock` 默认是非公平锁，使用 `new ReentrantLock(true)` 创建的则是公平锁。`synchronized` 也是非公平锁。

## 锁的状态与升级

> 版本注记：JDK 8～14 中对象锁有四种状态，级别从低到高依次是无锁、偏向锁、轻量级锁、重量级锁，其中偏向锁在 JDK 15 被默认禁用并标记为废弃（JEP 374），并在 JDK 18 中彻底移除（JDK-8256425）。在现代的 JDK 中，对象锁的状态实际是无锁 → 轻量级锁 → 重量级锁的三态升级路径。无论新旧路径，锁状态都只能升级不能降级。

`synchronized` 通过 Monitor 实现线程同步，而 Monitor 依赖于底层操作系统的 Mutex Lock（互斥锁）来完成线程阻塞与唤醒。

以 JDK 8～14 的四态模型为例，四种锁状态对应的 Mark Word 内容如下：

| 锁状态   | 存储内容                                                | 锁标志位 |
| -------- | ------------------------------------------------------- | -------- |
| 无锁     | 对象的 hashCode、对象分代年龄、是否是偏向锁（0）        | 01       |
| 偏向锁   | 偏向线程 ID、偏向时间戳、对象分代年龄、是否是偏向锁（1） | 01       |
| 轻量级锁 | 指向栈中锁记录的指针                                    | 00       |
| 重量级锁 | 指向互斥量（重量级锁）的指针                            | 10       |

四种状态的行为特征：

- **无锁**：没有对资源进行锁定，但同时只有一个线程能修改成功，其他修改失败的线程会不断重试。
- **偏向锁**：一段同步代码一直被同一个线程访问时，该线程会自动获取锁，降低获取锁的代价。其他线程尝试竞争偏向锁时，需要等到全局安全点才能撤销，撤销后可恢复到无锁或升级到轻量级锁。
- **轻量级锁**：偏向锁被其他线程访问时升级为轻量级锁，其他线程通过自旋的方式尝试获取锁，不会立即阻塞，从而提高性能。
- **重量级锁**：自旋超过一定次数，或者出现多线程竞争时，轻量级锁升级为重量级锁，此后等待锁的线程都进入阻塞状态。

## 可重入锁

同一个线程在外层方法获取锁之后，再进入内层方法会自动获取同一把锁，不会因为之前已经获取过还没释放而阻塞，这就是**可重入锁**，又名递归锁。这一特性可以避免同一线程多次获取同一把锁造成的自我死锁。

相对地，同一线程再次获取已持有的锁时仍会被阻塞的，是**非可重入锁**。

Java 中 `ReentrantLock` 和 `synchronized` 都是可重入锁；`NonReentrantLock` 则是 AQS 官方文档中用于示例的非可重入自定义锁。

可重入锁的实现机制：每个锁关联一个线程持有者和一个计数器。计数器为 0 时锁空闲，线程获取锁后将计数器置为 1；持有线程再次获取锁时计数器递增；线程每退出一次同步代码计数器递减，减到 0 时释放锁。

## 独占锁与共享锁

并非所有场景都要求资源只能被一个线程独占，于是出现了允许多个线程共同持有的**共享锁**。

- **独占锁（互斥锁）**：该锁一次只能被一个线程持有。`ReentrantLock` 是独占锁的典型实现，`synchronized` 同样也是独占的。
- **共享锁**：该锁可被多个线程同时持有。`ReadWriteLock`（读写锁）就是典型的共享锁实现。

在 `ReentrantReadWriteLock` 中，读锁和写锁是分离的：读锁是共享锁，写锁是独占锁。读锁的共享保证了并发读的高效，而读写、写读、写写之间则互斥。

独占锁与共享锁都可以通过 AQS 实现，区别在于同步器实现的方法不同。

## AQS

抽象队列同步器（AbstractQueuedSynchronizer，简称 AQS）是构建锁和其他同步组件的基础框架。它使用一个整型的 `volatile` 变量（`state`）维护同步状态，并通过内置的 FIFO 队列完成资源获取线程的排队工作。

## 对象头与 Monitor

### 对象头

对象头主要包括两部分数据：Mark Word（标记字段）和 Klass Pointer（类型指针）。

**Mark Word**：默认存储对象的 HashCode、分代年龄和锁标志位信息。这些信息都与对象自身的定义无关，因此 Mark Word 被设计成一个非固定的数据结构，以便在极小的空间内存储尽量多的数据。它会根据对象的状态复用自己的存储空间，也就是说在运行期间，Mark Word 里存储的数据会随着锁标志位的变化而变化。

**Klass Pointer**：指向对象所属类的元数据的指针，虚拟机通过这个指针来确定对象是哪个类的实例。

### Monitor

Monitor 是一种同步机制，通常被描述为一个对象。每一个 Java 对象都有一把看不见的锁，称为内部锁或者 Monitor 锁。

与对象关联的同步结构是 Monitor（HotSpot 中为 ObjectMonitor），其中 `Owner` 字段记录当前持有该锁的线程，表示这把锁正被该线程占用。线程私有的是 monitor record 列表：每个线程都持有一个可用的 monitor record 列表，系统中同时还有一个全局的可用列表。线程执行 `synchronized` 同步代码时，从自己的 monitor record 列表中取出一个 record，通过 CAS 把它与锁对象关联，关联成功后 record 中的字段指向对应的 Monitor，从而完成加锁。
